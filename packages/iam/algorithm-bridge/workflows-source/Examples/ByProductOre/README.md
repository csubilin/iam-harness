# 巷道掘进副产矿石量及金属量

这是「一句话 → 一张表」这条通路的第一个实例，也是流程格式的验证用例。
它现在是 `Workflows/Examples/` 下的**样板与回归夹具**，不是出厂能力：
`workflow_catalog` 只扫 `Workflows/*/manifest.json`，这里多一层，所以不出现在
`iam_workflow_list`。真实能力由用户在工作区固化得到。

```
一句话 ──①语义──► 选择子 ──②计算──► 本流程 ──③交付──► 表格 ──④固化──► 插件
        词汇表                        C++ 平台算法 + Python 接口   CSV      （确认之后）
```

本目录只有 ①②③ 的 ②③：一个能独立运行的 Python 程序、它的契约、它的术语表和它的测试。
①（把中文对到选择子上）属于使用阶段，④属于确认之后的事。

重复三角形清理、边连通壳分组在 GeomAlg 中实现；布尔重试与体积一致性检查、
按单元汇总矿石量和各金属量、体重类别归一化、覆盖率与报告合计均通过 IAM 的 C++
入口执行。Python 保留项目读取、选择子、参数检查及表格输出。块段单元表以原生
`MineCells` 句柄直接进入汇总，计算过程中不展开成 Python 单元字典；流程结束或失败
时统一释放句柄。接口、兼容性与验证记录见
[原生流程迁移记录](../../../../Algorithms/NATIVE_WORKFLOW_KERNELS.zh-CN.md)。

## 跑

```sh
python IAM/plugin/Workflows/Examples/ByProductOre/workflow.py \
  --project D:/dev/MiningFlatform/workspace/test1.iam \
  --block-model merge-2-dimine-block-model \
  --grade merge-2-dimine-cell-1:CU:1 \
  --density 2.7 --subdivide-max-size 3 \
  --out runs/by-product.csv --report runs/by-product.json
```

`--block-model` 用 **id** 而不是名字，避免按名字猜。

`--grade` 是 `列:金属:比例`，一种金属一次，可以给多次：

```sh
  --grade merge-2-dimine-cell-1:CU:1
  --grade merge-2-dimine-cell-2:PB:0.01
```

三段都必填。为什么，见「推不出来的参数，由使用者给」。

## 这张表说了什么

实测输出（`workspace/test1.iam`，33 条巷道）：

| 状态 | 条数 | 意思 |
|---|---|---|
| 已测量 | 1 | 副产体算出来了，块段模型圈定了，吨位与金属量都给了 |
| 无副产 | 5 | 判定过了：它到不了矿体，副产是 **零** —— 零是一个答案 |
| 未测量 | 27 | 没形成判断，原因在「说明」列里，用的是平台自己的原话 |

覆盖率 **18.2%**（6/33）。合计只覆盖这 6 条。**把 1 条的结果写成 33 条的总量，是这张表最
不该犯的错**，所以覆盖率和「其中有副产的条数」都印在表尾。

结果本身：480水平 与矿体相交，副产体 377.906 m³，圈定 32 个单元、500 m³，
体重 2.7 t/m³ 下矿石量 1350 t、金属量 CU 475.265 t。圈定体积的上下界是 [0, 2140]——
中心采样法在细长体上就是这么宽，报告如实给出而不是只给点估计。

**每种金属一列，列名带金属名**（`金属量_CU_t`），表尾的合计也按金属分开、并附上该列用的
比例。一个光叫「金属量」的数，在模型有好几个品位列时，读的人无从知道它是哪一种。

**矿石量只有一列。** 一个单元有没有体重，和有没有人化验过它无关；按金属各算一遍只会给出
同一个数，并诱导人把它们读成几堆不同的矿。

## 推不出来的参数，由使用者给，不给默认

这是这条流程的一条硬规矩，`--grade` 的三段就是它最直接的样子。

本数据集里**每一个字段**声明的单位都是 `1`、描述为空——包括 CU：

```
编号 unit='1'    CU unit='1'    距离CU unit='1'    类型 unit='1'    级别 unit='1'
```

所以「哪一列是品位」推不出来，「它的数是比例还是百分数」也推不出来。两样都得问：

* **金属名**：它给表里那一列命名。少了它，两次用不同列的运行会产出看起来一样、意思不同的表。
* **比例**：这是整个流程里**唯一一个错了不会响**的参数——把百分数列当比例读，金属量高
  一百倍，而那张表看上去毫无异样。所以它没有默认值。

同一条规矩在这条流程里还有几处：`--density` 无默认（模型里没有体重列）；矿体多于一个闭合
实体时**拒绝**而不是取第一个；术语表匹配为空时拒绝而不是给一张空表。

**能用数据表达的，就不写进代码；数据里没有的，就必须由人给。**

### 但「拒绝」不是终点：要问

流程跑在孙进程里，**问不了人**。所以缺参数时它做两件事，而不是把球丢回去：

1. **拒绝里说清缺什么**：「name the metal or metals… ask rather than pick」，比例那条会说
   两个可能的值分别是什么意思。
2. **候选由 `iam_mine_describe` 给**：它把每个列对应的**字段名、单位、值类型、是否数值**
   报出来。用户没法对着 `merge-2-dimine-cell-1` 回答「哪一列是品位」，对着
   `CU / float32 / numeric` 可以。

模型拿到这两样，就可以用 harness 的 **`ask_user_question`** 去问，带着真实选项、支持多选，
再把答案填回 `grades` 重跑。

**这三段是一条链，缺一段就不成立**：流程说不出缺什么 → 模型不知道要问什么；`describe`
报不出字段名 → 用户无从选；没有 `ask_user_question` → 只能猜。所以 `iam_mine_describe`
和 `iam_workflow_run` 的工具说明里都写着「推不出来就问，别猜」。

## 为什么 27 条没测出来

不是流程的问题，是源数据：

* **11 条是开放片体**。它们是各中段的 2D 平面图，本来就围不出体积。
  平台的原话：`The mesh is not closed: an edge of one triangle has no matching opposite edge`。
* **18 条含重复三角形**。同一个三角形出现两次，面积和体积都没有单值。流程会**在内存里去重后重试**
  （重复项对曲面不贡献任何含义，去掉它保持形状），源数据不动。
* 去重之后仍然不闭合的，如实留在表里。

看 `grep -c 未测量` 之前先看说明列：**「未测量」里的每一条都说得出为什么**。

## 怎么教它新词

「理解」这一半是数据，不是代码。术语表在 `glossary.default.json`，用户工作区的
`<工作区>/.iax/glossary.json` 优先：

```json
{ "terms": [
  { "term": "巷道", "selector": { "name_any": ["水平","斜井","竖井","斜坡道","回风井","小井"] } },
  { "term": "矿体", "selector": { "name_any": ["矿体"] } } ] }
```

选择子只读项目自己记录的东西——元素名、元数据（Dimine 导入会把来源图层写在 `layer` 里）、
父元素。不从几何类型反推：「这个面是 L 形」不是它成为巷道的理由。新增一个词就是加一行，
不用改代码、不用重新构建。

**匹配为空会被拒绝。** 一个匹配不到任何东西的「矿体」会产出一张全是 0 的表，而那张表和
一座没有矿的矿山长得一模一样。这条纪律和平台自己的 `filter` 一致：不点名任何类别就拒绝。

## 怎么固化成插件

跑通、确认之后，这个程序不需要改写就能被复用：`Workflows` 的包把它连同
`manifest.json` 一起发布，`AlgorithmBridge` 的 `iam_workflow_run` 按名字调用它。
「固化」不是把代码搬一个地方，是让一个已经验证过的契约变成可寻址的名字——
`manifest.json` 里的 `inputs` / `steps` / `acceptance` 就是那个契约。

## 这一轮不做

* 不实现自然语言理解（只用术语表）。
* 不建 office 插件（只出 CSV，接缝留给它）。
* 不回写源项目（副产体只进内存副本，源 `.iam` 一次都不改）。
* 不修源数据（重复三角形只在流程内去重）。

## 一个平台侧的缺陷，记在这里

当前流程调用 `geometry.boolean.intersection`：三角网先尝试 MeshAlg；超过每个操作数
8 个不同面平面等可回退的失败会转到 FacetModeler，随后才考虑已加载的 Provider。
以下数据来自迁移前**直接调用 FacetModeler** 的路径，不能当成统一调度后的失败率。

FacetModeler 布尔实现在真实 Dimine 网格上不稳定：历史实测约 **七成调用**以
`FacetModeler could not build a body from the triangle payload` 告终。三条对照：

* 同一网格的 `slice_plane`：30 次全部成功；
* 合成立方体之间的 facet 布尔：10 次全部成功；
* 失败与成功在**全新进程**里同样随机。

失败点在 `IAM/Algorithms/Source/IamAlgorithmCoreMesh.cpp` 的 `toFacetBody`
（`FacetModeler::Body::createFromMesh` 对含细碎三角形的网格返回空体），
不在本流程能修的范围内。

历史直接调用成功时结果逐位一致——12 次尝试里 4 次成功，全是 316 个三角形、
377.9063539952 m³。统一调度可能选择不同实现，其结果一致性尚未用该数据集复测；
流程仍比较两次成功的体积，一旦不一致就停止，而不是挑一个答案。
`BOOLEAN_ATTEMPTS` 的 40 次预算沿用历史直接调用的测量，并非当前路径的实测失败率。
